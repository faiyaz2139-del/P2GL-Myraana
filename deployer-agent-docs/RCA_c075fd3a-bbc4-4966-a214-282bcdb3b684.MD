# RCA — run c075fd3a-bbc4-4966-a214-282bcdb3b684 (p2g-production redeploy)

## Outcome
Deploy **failed** at `build_image` (Cloud Build `frontend-build` stage). The previous run (bf94d950) is still live and serving — nothing went down.

## Error (verbatim from build)
```
$ craco build
python3: can't open file '/backend/scripts/stamp_build_metadata.py': [Errno 2] No such file or directory
Error: Command failed: python3 /backend/scripts/stamp_build_metadata.py
    at Object.<anonymous> (/app/craco.config.js:11:3)
```

## Root cause (SOURCE / code — not a manifest or infra fault)
`frontend/craco.config.js` runs, **unconditionally on every production build**:
```js
if (!isDevServer) {
  execFileSync(
    "python3",
    [path.resolve(__dirname, "../backend/scripts/stamp_build_metadata.py")],
    { cwd: path.resolve(__dirname, ".."), stdio: "inherit" },
  );
}
```
This creates a build-time dependency on a sibling `../backend` directory and on `python3` + git. The farm `Dockerfile.cloudbuild` `frontend-build` stage builds the frontend in isolation — it copies **only** `frontend/ → /app` (`COPY frontend/ /app/`). So at build time `__dirname` is `/app` and `../backend/scripts/stamp_build_metadata.py` resolves to `/backend/scripts/stamp_build_metadata.py`, which does not exist in that stage → `execFileSync` throws → craco build exits 1 → build fails.

Secondary (would fail even if the script were present): `backend/scripts/stamp_build_metadata.py` calls `git_commit()`, which raises `SystemExit("Build metadata requires GIT_COMMIT or a Git worktree.")` when `GIT_COMMIT` is unset and there is no `.git` worktree — neither exists in the Cloud Build frontend stage.

This is new source behaviour: prior redeploys of the same template (bf94d950, a0116530, c3257343 …) succeeded, so the stamp invocation was introduced recently. The platform build layout (frontend-only frontend stage) is standard and correct; the code's cross-directory + git assumption is what breaks.

## Reproduced in eph sandbox (run source at /app/scratch)
1. Frontend-only layout, `NODE_ENV=production` → **exact build error**: `python3: can't open file '.../backend/scripts/stamp_build_metadata.py'` → node throws, exit 2.
2. Script present but `GIT_COMMIT` unset / no git → `Build metadata requires GIT_COMMIT or a Git worktree.` → exit 2.

## Verified fix (in-pod, both failure modes → exit 0, build continues)
Make the stamp step **fail-open** so a missing script / missing git degrades to a warning instead of killing the build — consistent with the file's own stated "fails open" philosophy for the overlay. In `frontend/craco.config.js`, replace the bare `execFileSync(...)` block with:

```js
if (!isDevServer) {
  try {
    execFileSync(
      "python3",
      [path.resolve(__dirname, "../backend/scripts/stamp_build_metadata.py")],
      { cwd: path.resolve(__dirname, ".."), stdio: "inherit" },
    );
  } catch (err) {
    console.warn(
      "[build-metadata] stamp skipped:",
      err instanceof Error ? err.message : err,
    );
  }
}
```

Verified in sandbox: with this wrapper, both the missing-`../backend` case and the missing-git case print a warning and continue (`BUILD CONTINUES`, exit 0).

### Optional hardening (if the build_metadata.json stamp is actually wanted in prod)
The fail-open fix unblocks the deploy but will *skip* stamping in Cloud Build. If the metadata file is required in the shipped frontend, the stamp must run in a context that has both `backend/` and a commit id — e.g. generate `build_metadata.json` before the Docker build and commit/copy it into `frontend/`, or pass `GIT_COMMIT` as a build arg and ensure the script's inputs are present in the frontend stage. Short term, fail-open is safe and sufficient.

## Who owns what
- **E1 (Code):** apply the fail-open edit to `frontend/craco.config.js` in the source environment, then re-trigger the deploy. The deployer agent did **not** mutate source and did **not** re-run the pipeline, because re-running on the unchanged code fails identically.
