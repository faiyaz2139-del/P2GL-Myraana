## (2) Why GET /api/build-info returns commit:unavailable — ROOT CAUSE CONFIRMED
Live probe (read-only GET, no creds): `GET /api/build-info` → HTTP 200 → `{"commit":"unavailable","builtAt":"runtime"}`.

Backend source `backend/server.py` lines 109–119:
```
@api.get("/build-info")
async def build_info():
    try:
        commit = subprocess.check_output(
            ["git", "rev-parse", "--short", "HEAD"],
            cwd=ROOT_DIR.parent, text=True,
        ).strip()
    except (OSError, subprocess.CalledProcessError):
        commit = "unavailable"
    return {"commit": commit, "builtAt": os.environ.get("BUILD_TIMESTAMP", "runtime")}
```
Root cause: `commit` is computed AT REQUEST TIME by shelling out to `git rev-parse --short HEAD`. The runtime container is not a git repo (the pulled source archive has no `.git`, and the platform-default farm Dockerfile neither preserves git history nor injects a `GIT_COMMIT` build arg). The subprocess therefore fails (OSError / non-zero) and the `except` branch returns `"unavailable"`. Likewise `builtAt` falls back to `"runtime"` because no `BUILD_TIMESTAMP` env var is injected by the build. This is a code+build-config design gap, not a deployment failure.

Fix direction (for E1/source owner): bake the commit at build time instead of reading git at runtime — e.g. pass `--build-arg GIT_COMMIT=...` / write a `build-info.json` (or set `BUILD_TIMESTAMP`) during build and have `build_info()` read that value, with the git subprocess only as a local-dev fallback. (NOTE: the standard Emergent source packaging strips `.git`, so any runtime-git approach will always yield "unavailable" in production.)
